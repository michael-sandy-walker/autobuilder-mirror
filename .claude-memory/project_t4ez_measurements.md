## The original plan (superseded in part -- see the ticket's corrections)

  - **Three directions, one chain (detail in the design note):**
    - **(1) Problem memory across runs AND projects.** Widens T4-CT (closed; same task only, keyed by the seed's SHA-256, 3 of 3 pairs shorter) from the exact signature to its SHAPE (the project's identifiers taken out structurally; a model only for what shape leaves). What transfers: the question that ended a shape, the form of the change that ended it, and "this was a framework defect fixed by a closed ticket" (a recurrence = a regression). Run knowledge answers the first two, memory knowledge (closed tickets' Observed / cause / fix) the third; the shape is the join key. Provenance, ADVISORY under T2-ER, imported knowledge judged before it binds (T2-FN).
    - **(2) A run that ends in a draft diagnosis** -- grind episodes, evidence lines, T4-EU's kind, similar past problems with provenance, a draft ticket in the roadmap's form. Yardstick: our own tickets filed from runs whose logs are still on disk, replayed; the share of drafts that match our diagnosis measures how much of the outer loop has moved inward. T4-EU's next slice lies on this direction.
    - **(3) Building itself, measured before trusted.** 534 of 643 ticket commits carry tests: start = the parent commit, input = the ticket body as it stood in the parent, judge = the commit's tests plus the parent's suite, held outside the copy. Rungs: an extracted module (structdiff-sized) -> a small ticket in the whole tree (586 files, 106k lines; an affected-tests gate; the local model's limits measured, [[project_local_first_constraint]]) -> the loop's own draft ticket from (2), judged by tests written before the run. A self-edit lands only through the user.
  - **First steps (offline, rules fixed before counting):** (a) normalise every recorded stuck signature (63 ledgers, the `stuck_outcome` actions) to its shape; count shapes in >= 2 projects, how often the same question ended them, how many match a signature quoted in a closed ticket; decision rule relative to T4-CT's within-task 10 of 19: comparable -> widen T4-CT's key to the shape; far smaller -> the cross-project value is the ticket match, folded into (2). (b) Direction 3's corpus script (parent, ticket body at the parent, tests added, change size, modules) and five rung-1 candidates. Then (c) direction 2's scoring sheet and 3-5 replays; (d) one rung-1 pilot.

  - **2026-11-17: the rule for the CASE measurement, written BEFORE counting** (`scripts/t4ez_cases.py`; 597 archived behaviour logs; a cycle's subgoal from its `cycle_start`; suffixed cycle ids (`-eval-tests`, `-tree-tests`) belong to their base cycle).

    - **Action (what the loop did next for that subgoal; first that applies):** rewind or pause; moved on (the next cycle works another subgoal); replanned (a `planning_run` before the next proposal on the subgoal); switched to the tests (the next proposal touches test files and the situation's mutation did not, or the reverse); retried the same files; changed other files. A situation with no later cycle in the run: no action, left out.
    - **Result:** R1 = the situation's subgoal reached COMPLETED by the run's end (the uniform result for every action, moving on included); R2 = the same situation key came back on that subgoal within the next 3 cycles (the bad result).

(Q3) does it carry to another project: leave-one-task-out, each held-out case gets the action with the best R1 rate for its key on the OTHER tasks (>= 5 cases) and, as the baseline, the best action overall (situation-blind); gap = R1 rate when the actual action equals the recommendation minus when it does not; compare situation-aware vs situation-blind gaps; permutation p from shuffling the situation keys. **A case memory is worth a slice when Q2 holds (gap >= 0.15, p < 0.05, in >= 3 keys) AND Q3's situation-aware gap exceeds the blind one by >= 0.10 with p < 0.05.** If only Q2 holds: actions matter but what worked does not carry -- recorded, and the reason prose (model reading) is the next lens.
